# ResearchClaw 后端测试、对照与调试总报告

截至 2026-11-10，后端按“本人使用的硕士科研助手”目标收工。当前可以用于论文定位、有来源的科研问答、idea 初筛、基线草案和同一会话中的研究方向校准。默认实现是 **LangGraph 单 Agent + 按需动态任务 DAG**，不是强制执行论文检索→创新→实验的固定工作流。实验执行仍需用户确认。本文集中解释测试过程及使用边界，不宣称系统绝对最优、科研结论自动正确或达到生产级服务标准。

## 2. 当前环境、数据和分工

沿用项目现有 Python 3.12 / `.venv`。后端在宿主运行；Docker 使用既有 PostgreSQL 和 Qdrant，不为本次整理新增服务或环境。环境总约束以[环境.md](环境.md)为准，本次不修改它。模型密钥仍只在原配置中，不进入报告。

当前正式知识库为 **204 份按 PDF 哈希区分的记录、3020 个 Parent、10955 个 Child**。204 不保证是 204 个独立学术作品：同题不同扫描或版本仍可能分别存在。PostgreSQL 存储正文、页码、关系、结构缓存、消息、session state、笔记及运行状态；**论文 dense 与 BM25 sparse 候选召回由 Qdrant 承担**，PG embedding 副本为 0，两类 Qdrant 点均为 10955。PG 的按 ID/哈希回读不属于候选召回。

最终 Agent 的[论文边界快照](agent-evidence/v20261110-architecture-live/paper-boundary.json)与 RAG 验收保持一致。本次仅文件归档，不运行论文入库、向量写入、数据库清空或模型重新测评。2000 份是配置保护上限，**不是已经完成的 2000 份容量压测**。当前可用规模是已测的 204 份；250–500 份为后续日常目标。

## 3. RAG：从结构探索到可核查问答

### 3.1 测了哪些改动，为什么没有一律采用“更复杂”的方法

首先比较原页级 Parent/词窗 Child 与论文结构解析候选，并对 GROBID、PDF 坐标、原始行和词坐标联合对齐做人工抽查。最重要的经验是：结构标题看似合理，并不保证子块完整、阅读顺序正确或检索命中后的上下文覆盖正确。

纯结构 Child 的早期 8 题直接证据命中从 **6/8 降至 3/8**，因此没有把全库迁到该候选。这只说明当时的解析、对齐和分组实现未胜出，不能证明语义分块本身无效。人工金标和对齐修正记录完整保留，供逐位置核对。

最终保留 `page-parent-word-child-v1`：页级父块、约 220 词子块与重叠；另加 `paper-section-evidence-v1` 章节证据层。只有命中 Child 完整落在已识别章节段内，才使用章节父上下文，否则回退页级父块；按命中位置聚焦约 500 词。也就是说，**结构用于证据归组与扩展，未虚称全库已切换为高质量语义 Child**。

查询端先理解意图、英文改写，按需产生至多两个同义/分步子查询与学术检索式；Qdrant dense 负责语义召回，BM25 sparse 补精确术语、方法名；RRF（k=60）融合排名，cross-encoder rerank，再组织带页码、来源和精确片段的证据。embedding 为 `BAAI/bge-small-en-v1.5`，384 维、归一化，离在线固定 revision；reranker 为 `ms-marco-MiniLM-L6-v2`。模型取舍与全链路解释见 [readme_rag.md](readme_rag.md)。

调试中修复过 Parent 聚焦丢失命中 Child、指定论文问题漂移到其他论文、评审引用 ID 格式解析不一致等问题。扩大测评还修正了早期参考答案依赖基线证据的偏置：改用源论文条件化参考，先冻结参考再进行被测召回。新旧协议的分数不能直接当时间序列涨分。

### 3.2 检索基线与消融

最终检索集 **60 题 = 48 开发 + 12 held-out**；生成集 46 题，两侧共享 41 题，共 65 个不同问题。题型包含事实/方法、跨篇、条件、排除、版本与结构定位。held-out 是跨题型划分，并非论文完全隔离，存在一对较相似的跨划分问题；标签是银标，不是专家穷尽标注。

|检索方案|开发 Recall@5|开发 ParentHit@10|held-out Recall@5|held-out MRR@5|held-out ParentHit@10|
|---|---:|---:|---:|---:|---:|
|dense|0.8438|0.5417|0.8333|0.6944|0.5833|
|BM25|0.7917|0.5833|0.9167|0.8472|0.6667|
|RRF|0.8750|0.5313|0.9167|0.8750|0.5833|
|RRF + rerank（full）|0.8542|0.7083|0.9167|0.9583|0.8750|
|balanced 候选|0.8542|0.5833|0.9583|0.8611|0.7083|

Recall 衡量已标相关论文覆盖；MRR 衡量首个相关论文位置；ParentHit 检查具体标注证据父块。RRF 有互补收益；rerank 的局部证据定位较好，但开发 Recall@5 低于 RRF，balanced 也没有全面胜出。因此保留对照，不宣称所有组件均提高全部指标。最终问答采用 anchored 策略，不能与论文搜索候选排序混为一个单变量实验。

### 3.3 生成质量与真实 RAGAS

生成 46 题 = 34 开发 + 12 held-out，开发中 5 题不可答单独评分，其余 29 题可答。配对银标中 legacy→anchored 的参考事实召回为开发 **0.6600→0.8386**、held-out **0.7142→0.7975**；精确引文覆盖为 **0.4655→0.5690**、**0.6389→0.7222**。开发忠实性 **0.9911→0.9845**，held-out 两者均 1.0000，说明改进不是每个指标都上涨。开发忠实性有效分母分别 28 与 29，其余开发项为 29。5 题不可答两组均正确拒答，不能外推为通用拒答率。

真实 **RAGAS 0.4.3** 在 held-out 12 题对 dense/anchored 各运行四项，96/96 个指标值成功计算：

|指标|dense|anchored|改善对应的实际用途|
|---|---:|---:|---|
|Faithfulness|0.9085|0.9156|减少回答偏离已给证据|
|Answer relevancy|0.5724|0.7358|更直接回应科研问题|
|Context precision|0.5889|0.6625|减少靠前的无用上下文|
|Context recall|0.5417|0.7083|覆盖更多参考答案所需信息|

原始证据：[RAGAS 汇总](rag-evidence/expanded-rag-v20261109/ragas-summary.json)、[配对比较](rag-evidence/expanded-rag-v20261109/paired-comparison.json)。RAGAS 忠实性 0.9156 不等于“91.56% 的答案完全正确”。生成与评审使用同模型体系，存在相关偏差；held-out 只有 12 题，配对参考召回的提升来自 1 题、11 题不变，bootstrap 区间跨及零，不宣称统计显著。

初轮 14 题检索、6 题生成也保留：当时 full 的 RAGAS Context recall 为 0.6472，低于 dense 的 0.9722；一项基线评分被提供方安全策略拒绝，有效 47/48。它是发现参考偏置与上下文遗漏的历史证据，不能用后来的 96/96 替换或抹去。

### 3.5 RAG 的不足会影响什么

跨篇参考事实覆盖仍低，开发约 0.54、held-out 约 0.45；150/10955 个 Child 超过 512 tokens，有 embedding 截断风险；后置附录、表格公式与版本识别存在缺口。有限上下文、多篇条件竞争、局部精排偏好与解析缺失都可能造成遗漏，不能凭总分断定唯一原因。

这些问题**会影响**完整自动综述、创新性裁决和误差保证证明，不能解释成“没有影响”。之所以仍满足当前目标，是本工具用于导航、初步问答和证据回读；用户可按篇追问、查看页码并核对 PDF。关键数学条件、模式/版本细节不能直接照抄模型答案。[人工抽查窗口](rag-evidence/expanded-rag-v20261109/人工抽查窗口.md)保留 10 个低覆盖案例、21 个源位置。

## 4. Session state、上下文与记忆

### 4.1 问题如何发现、实现如何改变

早期 30 题自建记忆实验预先写入了已确认答案，能证明记忆读取/替换/预算，却不能证明系统从自然聊天中找到事实；即使 30/30 也没有拿它冒充公开基准。之后用公开 LongMemEval-S 的 48 题子集暴露旧压缩短板：固定关键词、前 1200 字符与最后 24 条截取会丢失普通设备、较早事实和助手列表。

先改问题驱动 BM25，再过滤泛化词，为助手回答附上前一用户问题锚点，以约 900 字符、200 字符重叠的历史片段保留来源。这里切的是**聊天历史**，不是改变论文 Child 策略。历史跨会话试验开发从 2/24→15/24、保留从 3/24→17/24；该 48 题属于历史方向，不是当前跨会话记忆承诺。

用户随后收窄目标，当前只维护单会话：最近完整轮次 + 问题驱动旧消息检索 + 对话锚点 + 显式 State/已确认会话笔记 + 来源回读与 token 预算。新空白会话不自动继承旧私有记忆，只共享论文知识库。删除会话清理对应记忆及运行检查点。旧跨会话实现与证据保存，不继续优化、默认注入或重新宣传。

### 4.2 最终测试及分数

读取最终 [summary.json](memory-evidence/single-session-v20261110/summary.json)；它纠正过早期并发写入造成的一题旧基线汇总差异，初稿另存，不选择性重跑低分。

|范围|旧检索/压缩|当前问题驱动 + 对话锚点|
|---|---:|---:|
|LongMemEval 全部单会话 oracle，156 题|75/156，48.1%|135/156，86.5%|
|其中前轮未出现的 132 题|65/132，49.2%|116/132，87.9%|
|派生长历史 36 案例|6/36，16.7%|30/36，83.3%|

132 是 156 的子集，不相加。压力集来自 12 个问题各派生 20/50/100 轮背景，36 不是独立新增公共问题；轮数与事实位置绑定，不是严格控制变量的位置消融。oracle 已给对目标会话，不能拿它声称完整 LongMemEval-S 总分。评审是本地 LLM 银标，非官方 leaderboard 或人工金标。

另有 40 项后端回归，以及真实 LLM/API 的 100 轮场景：同会话找回 Jetson Orin NX 与误差界 0.006，修正为 0.004 后保留设备，空白新会话返回 UNKNOWN。它证明该具体科研参数场景可工作，不证明任意长会话无损恢复；不与公开题合并计分。

## 5. Agent harness/runtime：用实测决定架构

### 5.1 从三角色走到默认单 Agent

原 Planner/Worker/Reviewer 保留职责隔离，Planner/Reviewer 不执行工具，Worker 有白名单。但实测发现多角色重复传递上下文、取证过多、审查后没有交付综合答案等问题。压缩工具上下文后的一轮 24 题为旧单 Agent 22/24、三角色 21/24；更早非紧凑三角色仅 15/24、9 次运行错误。后续 3 题定向修复为 2/3 成功、3/3 证据支持，**不能将这三题替换进整组成绩**。

架构复核重新运行相同 24 题，随后单独测新 LangGraph 默认实现：

|指标|旧单 ReAct，复测|三角色，复测|新 LangGraph 单 Agent|
|---|---:|---:|---:|
|任务银标成功|22/24，91.7%|19/24，79.2%|23/24，95.8%|
|银标证据支持|22/24，91.7%|20/24，83.3%|23/24，95.8%|
|平均任务时间|51.938 秒|103.695 秒|50.446 秒|
|平均实际 tokens|19904.54|43129.67|21133.29|
|实际领域工具调用总数|84|150|73|
|运行错误|1|2|0|

证据：[配对架构报告](agent-evidence/v20261110-architecture-live/architecture-report.json)、[新实现逐题汇总](agent-evidence/v20261110-architecture-live/langgraph-validation-v2/task-summary.json)。相同配置模型、论文库和工具，但新组与旧组不是同批运行；题目已暴露、24 题很小、同模型银标，不作统计显著或等价性声明。真实连接 SSL/超时保留在旧组失败中，没有选择性重跑；多角色也有实质错误，差距不能都归因于网络。

测评上限：新单 Agent 10 次模型调用、18 次工具命令、180k tokens、200 秒；旧单也是 10 步，三角色为 20 次调用。正常 Web/CLI 默认上限为 24 次模型、18 工具、180k、240 秒，不能把测评平均时间当所有默认配置的服务 SLA。内部建图/提交命令不伪装成外部工具调用。

在当前个人读论文和草拟研究计划的任务上，三角色成本约翻倍而未得到质量回报，因此采用单 Agent。这个结论不表示多 Agent 普遍无效，也不否认角色权限隔离的工程价值；安全授权交给确定性宿主校验与用户确认，而非假定同模型 Reviewer 足够可靠。

### 5.2 自主性、工具与安全测了什么

LangGraph 使用真实 `StateGraph` 与官方 `PostgresSaver`，reason/tools/validate/advance/finalize 可循环。模型根据对话选工具、澄清或回答；有依赖时可生成最多 3 节点 DAG、提交阶段产物、一次局部重规划。已验收节点的契约与 hash 不能被重规划覆盖。同层目前串行，不宣传并行任务调度。

|验收项目|实际证据与边界|
|---|---|
|多工具选择|16 类意图 × 2 改写，32/32 路由正确；这是选择能力，不是 32 个科研问题完全解决|
|Skills|真实 discover/load/invoke 均有记录；该次科学答案仍 partial，不伪称任务全过|
|MCP|官方 SDK stdio，initialize/list/call 实际 wire；一个服务提供论文 metadata/chunk 两个只读工具，不虚报多个服务|
|动态 DAG|真实模型建立 context→queries 两节点，读取会话后生成 Scholar/arXiv 检索式，5 项验收通过；是明确要求建图的能力演示，不是自主规划成功率 100%|
|恢复|原生 PG 检查点 + dispatch 写前意图日志；显式恢复最多 2 次，复用已验收节点和已观察工具结果|
|不明确副作用|仅白名单只读工具允许重试；状态写入/skill/操作提案效果不确定时拒绝自动重放，不宣称 exactly-once|
|会话与身份|owner/project/session 绑定；旧 CLI 不可绕过 Web owner；状态/消息指纹改变后不允许恢复旧回合|
|高风险确认|下载、导入、coding 交接走独立认证确认；一次性票据、5 分钟有效；模型不能自行批准|
|删除|删除会话清理 journal 和 checkpoints/blobs/writes，论文共享知识库保留|
|Coding|保留原有 adapter 与确认交接；本轮不计入科研性能评估，不声称完成真实科研训练|

### 5.3 错误恢复的实际调试过程

最初一个 Agent 草稿误走旧 HybridRetriever，暴露历史索引路径；停止后改为正式已发布的 Qdrant 检索门面，核对论文库不变。随后发现工具返回中过大的向量/全文对象撑爆上下文，改为紧凑返回与按需原文回读。运行预算不足时安全 partial，不能把没有最终合成答案的取证过程当成功。

原生 Saver 首次并发初始化触发 `checkpoint_migrations` 建表冲突。加 PG advisory lock 后，故障注入又发现阻塞锁等待持有快照，使 `CREATE INDEX CONCURRENTLY` 等待形成死锁。最终用 `pg_try_advisory_lock` 短间隔轮询，补齐同项目并发首次初始化回归。保存初始失败 XML，不只保留修复后的绿灯。

Windows 深路径曾使测试工件写入报 FileNotFoundError，通过短测试工作区复现并验证，未删除业务断言来绕过错误。另有沙箱禁止外网的首轮 48 次全部零实际模型 token，单独保存为执行条件故障，不计科研能力分数。

最终工程回归 **121 项全部通过**；早期 111 项及相关 37 项有重叠，不加总为 269。新 LangGraph 科学评测 source 快照与交付源码保留为不同目录：最后工程差异是初始化等待方式，最终 121 项验证其修复；没有假称该次工程修复后再次重跑了全部付费科学题。

### 5.4 保留的科研失败与使用约束

新 Agent 唯一未通过题为 `fact-sz`：SZ 预测/量化/编码与绝对误差主干有证据，但把仅含 “be extended” 的 SDRBench 片段当作 PSNR 模式、2.1 版本细节依据。**引用 ID 存在不等于语义支持充分**。该题未重判、删题或选择性重跑。

因此它可辅助阅读、给候选创新点、准备基线比较；不能自动决定“此 idea 从未有人做过”，也不能自动保证所有误差界假设成立。涉及模式、版本、定理、误差保证的结论必须精确回读与人工核对。这个缺陷影响自动裁决，但不妨碍有来源的个人辅助工具定位；若将来改为自主科研执行，则必须重新设验收门槛。
